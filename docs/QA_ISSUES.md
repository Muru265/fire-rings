## Automation track — "fully automated Fire Rings with agentic alerts" (Muru's vision; Oracle stack)
Goal: the site keeps itself up to date and warns people automatically, run by AI agents, no human in the daily loop.

**Building blocks**
- **Oracle Autonomous Database (Always Free)** — stores worldwide near-real-time VIIRS detections (rolling 30–90 days), the published monthly record, calibration constants (frozen, versioned), alert subscriptions and an alert log. Oracle Spatial for area queries; ORDS for REST endpoints the site reads.
- **Ingest job** (DBMS_SCHEDULER or an OCI Function) — pulls NASA FIRMS NRT every ~3 h; applies the same filters (low confidence, known-static mask, region footprint); appends new detections; recomputes only the newest months (provisional) with frozen calibration; replaces provisional months when NASA standard data arrives (~5 months).
- **Monitoring agent** (OCI Generative AI Agents / AI Agent Studio, or Gemini) — after each ingest, checks every region/subscribed area: month-to-date vs same-days baseline, percentile, return period, live 72 h spike; decides whether an alert is warranted using fixed, documented rules (agent explains, rules decide).
- **Briefing agent** — writes a short plain-language alert/briefing grounded ONLY in tool results (same "numbers used" verification as Ask Fire Rings), including caveats (provisional, low activity, Punjab detection-time).
- **Alert delivery** — email (OCI Email Delivery) / webhook / optional SMS or Telegram; opt-in subscriptions per area with thresholds; alert log page on the site.
- **Site** — reads live endpoints instead of static JSON for the newest months; shows "auto-updated X h ago" and recent alerts.

**How the data flows once Oracle is in (answer to Muru, Tue):** NASA FIRMS API → Oracle (every ~3 h) → website. The 25-year archive is processed once by the existing Python pipeline and loaded into Oracle as-is; the scheduled job only adds NEW near-real-time days, recomputes the newest (provisional) months with the frozen calibration, and later swaps provisional months for NASA's final data. The site (and /api/ask) read Oracle's REST endpoints (ORDS) instead of static JSON. Recommended build: an **OCI Function (Python container) that reuses the existing pipeline code** (h3, filters, fire-days) and writes to Autonomous DB — easier and safer than rewriting H3/fire-day logic in PL/SQL. FIRMS key in **OCI Vault**, never in code; respect FIRMS limits (≤5 days per call, transaction limits per 10 min — per-region calls every 3 h are well within). Static JSON stays as the fallback if Oracle is down.

**Whole-world auto-download (Muru's question, Tue — extras/roadmap, not now):** Yes, possible. The FIRMS API serves the archive too (standard-processing sources for MODIS and VIIRS), a few days per call — so a script can walk the whole world day by day, 2000→today, and keep going automatically.
- **One-time backfill** on an **OCI Always Free Ampere VM** (up to 4 cores / 24 GB RAM free) running the existing Python + DuckDB pipeline — OCI Functions time out after a few minutes, so they're for the small 3-hourly updates, not the backfill. Rough size: thousands of API calls per satellite source; respect the MAP_KEY transaction limit (throttle + resume from the last finished day if interrupted) → hours to a day or two, not minutes.
- **Storage is the real limit**: raw global detections (hundreds of millions of rows) won't fit the free Autonomous DB (20 GB). Keep raw as compressed Parquet in Object Storage (or on the VM disk) and put only the small aggregates in Oracle (fire cell-days per H3 cell per day/month, calibration, baselines). If that's still too big: a small paid OCI tier, or aggregates only.
- **Automatic per-country calibration + validation gate**: every country gets its own exchange rate fitted on Jul 2012–Dec 2019 only; it's published only if it passes V1/V3; otherwise it's shown as "not validated" / "too little fire to judge". Nothing is shown that hasn't passed the same tests as the demo regions.
- **Then**: 3-hourly incremental updates (Function or cron on the VM), monthly recompute, alert agents on top.
- **Pitch**: "Every country, updated every 3 hours, each validated before it goes public." Demo shows the 6–7 validated regions; the world-wide backfill is the roadmap (or a small live proof if time allows).

**Safety rules for alerts**
- Thresholds are deterministic and documented; the AI never invents numbers (server-side number check).
- Every alert carries caveats and is labelled provisional; low-activity guard prevents false "+400%" alarms.
- Rate limits / de-duplication so one event doesn't spam subscribers; human-readable unsubscribe.
- Positioning: planning/situational alerts ("this area is far above normal this month"), not a replacement for emergency calls or national fire services.
